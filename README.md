# The Racing Kings Master

**The Racing Kings Master** is a community-driven website for the competitive **Racing Kings** chess variant. It provides a central place to recognize players who earn official Racing Kings titles, display title holders, browse members, check title eligibility, and manage community features.

The project is currently built as a web application using HTML, CSS, JavaScript, Python, and Supabase. The repository is also designed to work with Replit for development and deployment.

> **Important:** This README describes the current structure of the repository. Some files are legacy, experimental, or generated by development tools. They are documented below so that it is clear what they are and whether they should normally be edited.

---

## 1. What the website does

The website is centered around an official Racing Kings title system.

Main features include:

- 🏆 **Leaderboard** — Shows titled players and site members, with player information and ratings where available.
- ♛ **Titles** — Explains the different Racing Kings title levels and their requirements.
- 🔍 **Title Checker** — Allows a player to check whether their Lichess Racing Kings activity appears to satisfy title requirements.
- 👤 **Profiles** — Provides player/profile pages with relevant information and title history.
- 📋 **Players** — Lists officially recognized titled players.
- 📰 **News** — Displays Racing Kings Master news and announcements.
- 👥 **Membership** — Users can register and become members of the site.
- 💬 **Chat/messaging** — Supports communication features between users and administrators.
- 🔐 **Authentication** — Registration and login are handled through Supabase Auth.
- 🛠️ **Admin features** — Administrators can manage applications, users, notifications, and other community functions.

The homepage loads live statistics and the newest members from the backend rather than relying entirely on hard-coded numbers.

## 2. Technology overview

The project uses several technologies that work together:

### Frontend

- **HTML** — Page structure and content.
- **CSS** — Visual design, layout, responsive/mobile styling, and animations.
- **JavaScript** — Dynamic behaviour, menus, authentication integration, news, API calls, and other interactive features.

### Backend

- **Python / Flask** — Provides server-side API routes and serves the website when the Flask application is used.
- **Supabase** — Used for the modern authentication/database system.
- **SQLite code** — `db.py` contains an older/local database layer that is still present because some legacy backend functionality remains in the repository. The frontend authentication path is intended to use Supabase Auth.

### External services

- **Lichess** — Used for player information, Racing Kings ratings/activity, and title-checking functionality.
- **Supabase** — Authentication and database services.
- **Replit** — Development/deployment environment used by the project.

# 7. Supabase

Supabase is the current database/authentication platform being integrated into the website.

The project uses Supabase for modern user authentication and database-backed website functionality.

The frontend connection is handled through:

- `js/supabase.js`
- `js/auth-supabase.js`

The Supabase project should be treated as the source of truth for current registered users and database-backed data where the feature has been migrated.

### Important distinction

There are currently two kinds of data you may encounter:

1. **Supabase data** — Current database/authentication data.
2. **Static repository data** — JSON or other files stored directly in GitHub.

Do not assume that changing one automatically changes the other.

# 8. Player and title data

The project has historically used static player data as well as database-backed member data.

The static player/title data should only contain **real, officially recognized titled players**. Placeholder/test players should not be added to the production data.

When adding a real titled player, first determine which system the page currently reads from. Do not create a second source of truth accidentally.

# 14. How the main website works

A simplified version of the architecture is:

```text
User's browser
      │
      ├── HTML pages
      │
      ├── CSS
      │
      └── JavaScript
             │
             ├── Supabase Auth / Database
             │
             ├── Flask API
             │
             └── Lichess API
```

For example, the homepage:

1. Loads `index.html`.
2. Loads shared styling from `css/global.css`.
3. Loads shared JavaScript such as `js/menu.js` and `js/supabase.js`.
4. Requests statistics from the backend.
5. Requests the newest members from the backend.
6. Displays the returned information dynamically.

This means some information visible on the website is **not stored directly inside the HTML**.

# 15. Working with the project if you are not a programmer

The safest approach is to describe the change clearly to an AI coding tool such as Replit Agent rather than manually editing many files.

For example:

> "Change the leaderboard so titled players are sorted by title first, then rating. Do not change authentication or the database structure."

Good instructions should say:

- what you want changed
- which page/feature it affects
- what must NOT be changed
- whether the change should affect mobile, desktop, or both

Before accepting a large change, check the GitHub diff so you can see which files were modified.

# 16. Important development rules

### Do not hard-code real users unnecessarily

Registered users should come from the database/authentication system where appropriate.

### Do not create placeholder production data

Test users are useful during development, but they should not remain in production player/title data.

### Keep authentication centralized

The current intended authentication system is Supabase Auth. Avoid creating another independent login system.

### Keep shared code shared

If something is used on many pages, put it in the appropriate shared CSS/JS file instead of duplicating it on every page.

### Be careful with database changes

Database schema changes can affect authentication, profiles, leaderboard information, applications, and other features. Test them before deploying.

### Keep mobile support

The website is intended to work on both desktop and mobile screens. New UI should be tested at smaller widths as well.

# 17. Adding a new title

When adding a new Racing Kings title, update all relevant places rather than changing only the title page.

Check at least:

1. Title requirements/documentation.
2. Leaderboard display/sorting logic.
3. Player/profile display.
4. Title Checker requirements.
5. Any title statistics.
6. Images or certificate areas if applicable.
7. Any JavaScript/JSON/database structures that use title codes.

Use a short, consistent title code (for example `RKCM`, `RKIM`, etc.).

---

# 18. Adding a new member or titled player

### Normal member

A normal registered member should normally be created through the site's registration system and stored in Supabase.

### Titled player

A titled player should only be added after the title has actually been awarded/approved according to the project's rules.

Make sure the player's title information is added to the correct current data source and that the leaderboard/profile pages can see it.

Do not simply add a player to an old JSON file without checking whether that file is still being used.

# 21. Before making a major change

For a significant change, use this checklist:

- [ ] Identify which page/feature needs changing.
- [ ] Find the HTML, CSS, JavaScript, and backend files involved.
- [ ] Determine whether the data comes from Supabase, Flask, Lichess, or a static file.
- [ ] Make the smallest reasonable change.
- [ ] Test the feature on desktop and mobile.
- [ ] Check authentication/admin permissions if relevant.
- [ ] Check the GitHub diff.
- [ ] Make sure unrelated files were not changed accidentally.
- [ ] Commit/push only after the result looks correct.
